## 这是什么

review-bounded 是一个 [Agent Skills](https://agentskills.io/specification)（SKILL.md）包：在当前分支上编排**恰好三轮** review-and-fix——所有问题按同一把固定标尺打 P0-P3，每轮修复前征求你的授权，三轮后给出是否收敛判定。

其他有界审查工具是平台插件、sub-agent 原语或 CLI 工具。而 review-bounded 是一个**Skill**：纯 SKILL.md，零运行时。任何能读 SKILL.md 的 agent 都能跑它。

## 为什么 AI review 永远没有终点

```
“review 一下当前改动” → 发现问题 123 → fix
“再 review” → 又发现问题 456 → fix
“再 review” → 又发现问题 789 → fix
“再 review” → ……
```

这个循环的起点是**工程纪律**，AI 发现问题并修复之后，任何一个负责的工程师都会想验证修复，而不是不检查就提交。而 Code Review 正是验证修复的一种重要方式。所以下一步顺理成章：再 review 一次——然后就发现了新问题。

而下一个修复同样需要验证，于是开始循环往复。

AI 做 code review **基本不存在“零问题”终点**——这不是某个模型的缺陷，而是结构性的：

- **任务本身没有终止条件。** “Review 这段代码”的意思是“找问题”，不是“确认它足够好”。人类审查者会因疲劳、时间压力或信任而停止；LLM 没有这些——每一次调用都是独立的采样，带着同一个开放目标。
- **训练分布奖励“发现问题”。** 被标注为 bug 的代码片段携带最高的信息权重，模型在统计上学到了“找出问题”是高价值输出，而“这段代码没问题”是低价值噪音。LLM 也学会了人类审查者早就懂的道理：永远只说 LGTM（Looks Good To Me）的人，很快就不会被请去 review 了。
- **每一轮读的都是完整代码，而不是修复本身。** 每轮 review 的输入是修复后的整个代码库——而不是“只验证上一轮的问题是否解决”——所以新一轮总能提出上一轮没看到的东西。

所以“再 review 一次”永远能找到更多问题。真正的问题不是 review 能不能找出问题——而是**剩下的问题还有多严重**，以及它们是否已经轻到可以接受。

## 为什么叫“有界”（bounded）？

因为让无限循环停下来，最直接可靠的方法，就是事先承诺次数——三轮，不多不少。

## 核心：问题更轻，而不是问题为零

AI review 永远到不了零，但它**收敛**：严重度逐轮下降。

```
Round 1:  死锁、数据丢失、安全漏洞            (P0/P1)
Round 2:  性能、健壮性、错误处理              (P2)
Round 3:  命名、死代码、风格                 (P3)
```

这不是运气：问题的采样服从 **Zipf 式分布**——最显著的问题（死锁、数据丢失、注入）先被抽走，后面的轮次只能从长尾里采样（命名、死代码、风格）。严重度逐轮下降，是因为同一个分布在按顺序被采样——不是模型变聪明了，也不是它变累了。判定上，持平（不上升）也算收敛——逐轮下降是典型轨迹，不是硬性要求。

代码审查的目的**不是**“确认彻底没有问题”（这也不太可能），而是确认检查出来的问题**严重程度较轻，可接受**——并且有数据度量支撑，而不是靠感觉来判断。

本 skill 让收敛可度量，让“停止”成为你能站得住的决定。这四点，正是其他 Code Review 插件/扩展很少给你的：

1. **恰好三轮，不多不少**——固定次数，让“再 review 一次”不可能变成无限循环；只 review 一遍，你肯定不放心，连回归验证都不做吗？可 review 次数过多，那啥时候是个头？
2. **三轮共用同一把标尺（P0-P3）**——“问题是不是变轻了”变成数字，而不是感觉；三轮 P1→P2→P3，趋势一目了然；
3. **每轮修复前征求授权**——AI 提议，你拍板；没有你的同意，代码不会被改动，永远没有自动修复；
4. **收敛/未收敛判定**——AI 准备说“已经没啥问题了，可以考虑合并了”，但规则要求它先自我反驳：列出反对合并的理由。理由都合理有力，说明还有问题；都是些鸡零狗碎、不值一提的东西，才说明真的可以合并。拿不出有力的反驳理由，那才算真正没问题了。

## 快速开始

要求：任何支持 Agent Skills 标准的 coding agent（Claude Code、Codex、ZCode 等）。

**安装**——一条命令：

```sh
npx skills add ZM-BAD/review-bounded
```

**发起**——在 agent 会话里：

- ZCode / Claude Code：`/review-bounded`，或直接说“跑三轮 CR”、“对这个分支做有界 review”；
- Codex：自然语言——“run three rounds of bounded code review on this branch”（没有斜杠命令）。

开始时由你选择审查范围——当前代码与基准分支的对比、仅未提交改动、当前分支最近若干 commit、或你自己指定的任意范围。然后 skill 跑恰好三轮，给你一个判定。

> 仅交互式使用：按轮授权和提交决策需要人参与；非交互模式（如 `-p` 一次性执行、CI）不支持。

## 判定长什么样

```text
判定：收敛

关键问题 1（严重度趋势）：三轮最高级别 P1→P2→P3，P0+P1 数量 2→1→0
关键问题 2（fix 回归）：未检测到——三轮测试通过 + diff 追溯
关键问题 3（最后一轮问题）：R3-1（P2，边界）：仅在异常输入时出问题

反对合并的理由：
1. 新增缓存模块没有淘汰路径（代码证据）
2. 端到端验证未运行（测试证据）
3. 两个辅助函数命名偏离约定（推测）

最后一轮问题的上线影响：
- 必然出问题：无
- 可能出问题：异常输入下（R3-1 场景）
- 不会出问题：正常输入路径

未修复项（未授权 / 未修复的 P2/P3）：
- [ ] R2-2：重试逻辑无退避（建议处理方式）
```

**收敛**意味着最后一轮的问题很轻，没有发现修复引入的回归，所有未决事项都在清单里。**未收敛**意味着最后一次 review 依旧发现了问题，且不建议忽略——继续 review-and-fix 是正确的选择。

## 工作方式

1. **第一轮**：按初始确认的审查范围（当前代码与 main/master 的对比 / 仅未提交改动 / 最近若干 commit）审查，汇报问题（P0-P3），征求授权，在工作区修复（不提交），跑回归检查（有测试/lint 就跑）。
2. **第二轮**：重新读取最新代码（禁止凭记忆），优先看上一轮 fix 的增量和未覆盖的类别，与第一轮去重，然后同样的循环：汇报 → 授权 → 修复 → 验证。
3. **第三轮**：同一循环，然后输出最终判定。全部修复均未提交，由你决定是否提交、如何提交（单 commit 或按 finding 分组）。

每一轮都通过 `git diff` 和重新读文件审查**实际最新代码**，绝不凭记忆重构。修复只改工作区、**过程中不提交**；最终判定后向你展示全部修复清单，由你决定是否提交及如何提交。轮次记录保存在对话内，**不产生额外文件**（用户要求留档时，agent 才把汇总写入 `REVIEW.md`）。

## FAQ

- **三轮够吗？** 判定会回答这个问题：收敛说明剩余问题很轻，没有隐藏项；未收敛会明确指出还存在哪些问题。
- **支持我的语言/框架吗？** 它是语言/框架无关的 skill，不是 linter：agent 能读什么（代码、测试、文档）就能审什么。无运行时、无依赖。
- **不是已经有有界审查工具了吗？** 有——Convergo、adversarial-review 等，恰好验证了方向。区别：它们平台绑定（插件、子会话原语、双 CLI），且大多自动修复、无逐轮授权；而我们是**纯 Skill**，零平台锁定，一条命令安装。
- **改动很小也要跑三轮吗？** 不需要——单行或纯文档改动，一轮就够。

## 目录结构

```
SKILL.md                  # 编排核心：轮次循环 + 记录方式 + 铁律
references/
  rubric.md               # P0–P3 严重度标尺 + 审查类别清单（第一轮前加载）
  round-prompt.md         # 单轮指令：最新代码 / 去重 / 证据 / 授权 / 回归检查
  decision-rules.md       # 三轮后收敛判定规则 + 反对合并的理由 + 输出格式（中英模板）
```

## 设计原则

- **编排层，非执行层**：执行用 agent 原生工具（git、文件、Bash）和项目已有测试/lint，按 `references/round-prompt.md` 内置指令直接执行，不委托其他审查 skill。
- **零运行时**：纯 Markdown，无脚本、无依赖、无 API，可移植到所有支持 SKILL.md 标准的 agent。
- **结构性约束写死**：第一轮前固定 rubric，每轮修复前征求授权，“不确定一律未收敛”，判定前必须先自我反驳——这些不依赖模型自觉。
- **每轮都是新代码**：记忆永远不能替代读取仓库真实状态。
